## 0. 施工纪律（每一期都适用，别跳）

1. **不做半成品期**：每期结束时必须有一个**能跑起来的程序**，而不是"库写好了但画不出来"。
2. **每期都要有机器判据**：读回像素/深度、headless 断言、draw call 与 CPU 统计。
   并且要证明这条判据**能抓住它针对的 bug**（故意破坏一次，看它报不报）。
3. **每期结束跑完整门禁**（见第 7 节），一项都不许跳。
4. **边界不放宽**：3D 代码只放 `include/glimmer/` + `src/glimmer/`，只依赖 glimmer 自身与
   third_party；新增示例**只链接 `libglimmer.a`**，由边界脚本规则 3 强制。
5. **2D 渲染器冻结**：`lum_renderer2d` 只修 bug，新能力一律进 3D 路径。
6. 每期完工：勾第 8 节台账 → 更新本文档状态列 → 补 `SKILL.md` 里新踩到的坑。

## 1. 落位决定（已定；要推翻请先改本节）

| 项 | 决定 | 理由 |
|---|---|---|
| 代码位置 | `include/glimmer/` + `src/glimmer/` | 3D 渲染器是**平台**的一部分，不是引擎高层的插件 |
| 构建目标 | **放进现有 `glimmer` 目标**，不新开 `glimmer3d` | 不新增 CMake 结构，现有边界三规则自动覆盖新代码；等 3D 代码涨到约 2k 行再考虑拆目标 |
| 文件命名 | 新文件 `include/glimmer/{camera3d,mesh,renderer3d,…}.h` | 目录已经叫 glimmer，文件名前缀冗余 |
| 符号命名 | **沿用现有的 `lum_*` / `Lum_*` 与 `lum_*.h` 文件名**（用户 2026-09 决定） | glimmer 内的既有代码全是 `lum_*`，同一个头里混两种前缀比"欠一笔债"更糟；统一重命名仍留到"阶段 2"一次性做 |
| 示例 | 新增 `glimmer_hello3d.c` → 目标 `glimmer_hello3d`，**只链接 `libglimmer.a`** | 复刻 `glimmer_hello` 的独立运行判据 |
| GL 版本 | **停 3.3 core**（现状见 `src/glimmer/lum_window.c:42-47`） | 有 instancing / UBO / 纹理数组 / MSAA / sRGB；**没有** SSBO 与 multi-draw indirect（4.3+）→ GPU-driven 只能作为可选末期 |

## 2. 现状与硬约束（决定了分期顺序）

| 事实 | 出处 | 对 3D 的含义 |
|---|---|---|
| 3.3 core + forward compat 写死在窗口创建处 | `src/glimmer/lum_window.c:42-47` | GPU 剔除/间接绘制不在能力集内，M1~M9 全走 CPU 提交 |
| 2D 渲染器的合批键与"CPU 烘几何" | `src/glimmer/lum_renderer2d.c:367-388` | 不能复用为 3D 管线；3D 走独立命令与提交路径，只共享 GL 包装件（shader/texture/material/rt） |
| 数学层零引擎依赖但缺整条 3D 管线数学 | `include/glimmer/lum_math2d.h`（72 个公开函数，实测：vec2 19 / mat4 14 / vec3 13 / vec4 8 / rect 6 / 谓词 4 / 角度 2 / 其它 6） | 缺 perspective、look_at、四元数、Mat3、cross、TRS、Frustum；补这些约 300~500 行 |
| RenderTarget 只有 color + 可选 depth RBO，无 MSAA/MRT/HDR | `include/glimmer/lum_render_target.h:9-16` | 阴影、后处理、HDR 的前置条件 |
| 纹理只有 5 个标志，无 sRGB/浮点/立方图 | `include/glimmer/lum_texture.h:18-25` | 颜色正确性与阴影贴图的前提 |
| uniform 位置每次都 `glGetUniformLocation`，无 UBO | `src/glimmer/lum_shader.c:118-121` | M1~M4 用朴素 uniform 可行（物体少），**M5 必须上 UBO** |
| 默认帧缓冲有深度位（GLFW 默认 24 位） | 无需改代码 | **M1 不需要动 RenderTarget**，深度测试直接用默认帧缓冲 |
| ECS 视图上限 3 组件；序列化字段种类无 Vec3/Mat4；`Transform` 是 2D | `include/lum_ecs.h:61-63`、`include/lum_serial.h:95-103`、`include/lum_scene.h:41-45` | 只挡**引擎侧接入**（M9），不挡渲染器本身 —— 渲染器只吃矩阵 |

## 3. M1 · 最简 3D 渲染器（逐文件拆解）

**目标**：一个带透视相机、带深度测试、能画一批三角形的渲染器。**不碰 2D 路径**。

| 文件 | 内容 | 行数（估） |
|---|---|---|---|
| `include/glimmer/lum_math2d.h` + `src/glimmer/lum_math2d.c` | 只补 3D 最小集：`lum_mat4_perspective`、`lum_mat4_look_at`、`lum_mat4_rotate_x/y`、`lum_mat4_transpose`、`lum_vec3_cross` | +30 / +150 | **+19 / +87** |
| **并入** `include/glimmer/lum_camera.h` + `.c` | `lum_Camera3d`（position / target / up / fov / near / far）→ view / proj / VP + 轨道运动。与 `lum_Camera2d` 同文件（两种相机模型，见 glimmer.md） | — | 43 / 71（并入后 camera.h 85 行 / camera.c 172 行） |
| `include/glimmer/lum_mesh.h` + `.c` | `lum_Vertex3d`（pos3 + normal3）、`lum_Mesh`（GPU 常驻 VAO/VBO/EBO）、内置 `lum_mesh_create_box`；几何生成与上传**分成两半**（前者可 headless 测） | 60 / 140 | 53 / 153 |
| `include/glimmer/lum_renderer3d.h` + `.c` | init/shutdown、`set_viewport`、`begin_frame/end_frame`、`clear`、`set_camera`、`set_depth_test`、`draw_mesh(mesh, model, color)`、内联最小着色器、draw call/三角形统计 | 95 / 280 | 68 / 149 |
| `glimmer_hello3d.c` | 独立示例：两个**前后重叠**的立方体、轨道相机、`[D]` 切换深度测试（A/B） | 130 | 109 |
| `glimmer_check.c` | **无窗口回归检查**：3D 数学 / camera3d / mesh 的纯 CPU 一半（计划外新增，值） | — | 244 |
| **合计** | | **≈ 1035** | **1022**（误差 1.3%） |

> 估算准的原因不是运气：**先把"要断言什么"写清楚再写代码**，行数自然不跑偏。
> 这条值得带到 M2~M9 —— 每期的"验收判据"列先填，再动手。

### M1 验收（四条，全部机器可判）

1. **headless 数学**：已知点经 `look_at × perspective` 的投影与手算值一致（±1e-3）；
   相机 VP 的逆能把 NDC 点还原回世界点（往返一致）。
2. **读回颜色**：两个立方体**重叠区域**必须显示**近的**那个的颜色 ——
   这是"深度真的生效"的唯一有效判据（只画一个方块证明不了任何事）。
3. **读回深度 + 开关 A/B**：重叠区 `glReadPixels(GL_DEPTH_COMPONENT)` 是近物体的深度；
   按 `[D]` 关掉深度测试后，同一区域变成"后画的赢"。
4. **门禁与独立性**：`glimmer_hello3d` 链接行不含 `Luminous`；全量构建 0 warning、
   严格集 0、公共头自包含、`Luminous_rts_check` 41 组 / 198 断言全绿、四个老冒烟零回归。

### M1 实测结果（2026-09 完成）

| 判据 | 实测 |
|---|---|
| headless（`glimmer_check`，无窗口） | **52 条断言 / 0 失败**；含近/远平面 → NDC ∓1、90° 视场下 ±1 落在 NDC 边界、世界→NDC→世界往返、旋转手性、(AB)ᵀ=BᵀAᵀ、退化参数不外溢 NaN、立方体 24 顶点/36 索引/8 个角 |
| 深度 A/B（读回颜色 + 深度） | 深度开：中心像素 `(141,62,42)`＝**近方块**，深度 `0.97628`，后方块可见 `16504` px；深度关：中心像素 `(20,41,68)`＝**远方块**，后方块可见 `20356` px（近方块挡住的那 3852 px 回来了）；只画远方块时深度 `0.98625` > 前者的 `0.97628` |
| 独立运行 | `glimmer_hello3d` 链接行不含 `Luminous`（边界脚本规则 3 已推广到所有 `glimmer*` 目标并 A/B 验证） |
| 门禁 | 32 个 `.c` 严格集 0（含 `-DLum_Debug`）；公共头 39/39 自包含、glimmer 21 个头只给 `-Iinclude` 也过；`rts_check` 41 组 / 198 断言全绿；6 个可执行冒烟全绿（`glimmer_check` 57 断言） |
| **每帧耗时基线**（RTX 5060 / GL 3.3，960×600，60 帧均值） | 仅窗口+输入+时间+swap **0.59 ms**；+清屏 **3.93 ms**；+两次 `draw_mesh` **4.16 ms** ⇒ 240 帧约 1 秒。**M2 的实例化要跟这个数比**（对照项：1000 / 10000 实例的每帧毫秒与 draw call 数） |

> 上面那行基线是用临时分段计时探针量出来的（探针用完即删）。**量的过程本身避免了一次误判**：
> 冒烟里 `glimmer_hello3d` 曾"永远不退出"，第一反应是性能退化 —— 实测每帧只有 4.16 ms，
> 真正的原因是**示例循环的帧上限被外部改动删掉了**（见 SKILL 诊断手法 18）。
> **先量再猜**，这条在诊断手法里排第一。

**探针抓到的第一个真 bug**（值得记下来）：`lum_renderer3d_begin_frame()` 原本每帧都把深度状态
恢复成默认，于是调用方刚设的 `set_depth_test(false)` 被覆盖 —— 深度开/关两次读数**完全相同**，
开关等于失效。修法是明确状态归属：**深度是"模式"，帧初不重置；`begin_frame` 只重置统计**。
这就是"每期必须有能抓住它针对的 bug 的判据"的实例：只跑不读回的话，这个 bug 会一直躺在库里。

### M1 拆成两个子提交（便于验证与回退）

- **M1a**：数学 + `camera3d` + `mesh`（≈ 520 行）+ headless 断言。
- **M1b**：`renderer3d` 最小版 + `glimmer_hello3d` 双立方体深度 A/B（≈ 510 行）
  + 读回判据 + 边界脚本规则 3 推广到"所有 `glimmer*` 示例"。

## 3b. M2 · 实例化（已完成）

**目标**：同一个 mesh 画几千上万个，别让 CPU 死在提交上。

**设计决定：模型矩阵改走顶点属性，只保留一条绘制路径。**

M1 里 model 是 uniform（`u_model`），每个物体要单独设一次；M2 把它改成**每实例的顶点属性**
（location 2..5 各一列 mat4，`glVertexAttribDivisor = 1`）。于是：

```c
lum_renderer3d_draw_mesh(mesh, model, color)
    ≡ lum_renderer3d_draw_instanced(mesh, &model, 1, color)
```

`draw_mesh` 就是"画 1 个实例"，**没有第二条着色器路径**。好处：实例化这条路每帧都在被走，
不可能悄悄腐化（M1 的深度示例与探针跑的也是它）；代价是 `draw_mesh` 每次都上传 64 字节（可忽略）。

实现要点（都在 `src/glimmer/lum_renderer3d.c`）：

| 点 | 做法 | 为什么 |
|---|---|---|
| 实例矩阵缓冲 | 渲染器自有 VBO，容量按需增长、永不缩小 | 一个 mesh 可以被任意多个实例复用，缓冲不该属于 mesh |
| 上传 | 小批量直接 `glBufferSubData`；≥256 个先 `glBufferData(...,NULL,...)` 孤儿化再写 | 大批量每帧重写时避免驱动等待上一帧用完 |
| 实例属性配置 | 每换一个网格做一次（缓存命中即跳过） | location 2..5 指向的是渲染器的缓冲，与网格数据无关，配一次就长期有效 |
| draw call | `glDrawElementsInstanced`，**与实例数无关，恒为 1** | 这正是 M2 的全部意义 |

### M2 实测结果（2026-10，RTX 5060 / GL 3.3，960×600，关垂直同步）

| 组 | draw calls | 三角形 | 提交耗时（中位） | 整帧 |
|---|---:|---:|---:|---:|
| N=1000 实例化 | **1** | 12000 | **0.012 ms** | 0.144 ms |
| N=1000 逐实例提交 | 1000 | 12000 | 2.023 ms | 3.123 ms |
| N=10000 实例化 | **1** | 120000 | **0.031 ms** | 0.154 ms |
| N=10000 逐实例提交 | 10000 | 120000 | 17.760 ms | 29.981 ms |

⇒ **提交耗时降 169×（1000）/ 573×（10000）；整帧 22× / 195×** —— 后者的实际含义是
一万个立方体从 **34 fps 变成约 6500 fps**（同样的画面、同样的三角形数）。

判定正确的两条独立判据（缺一不可，因为"16 个实例全叠在同一个地方"也是一次 draw call）：

| 判据 | 实测 |
|---|---|
| **位置正确性**：用相机矩阵把每个实例中心投影成屏幕像素，逐点采样 | 4×4 共 **16/16 命中**；网格中央的空档**未**被点亮（不是画成一片实心） |
| **与逐实例提交图像一致** | 亮像素数 **170576 = 170576，差 0**（若叠一处会少掉 159915） |
| M1 判据在新通路的复验 | 深度 A/B 逐位复现 M1 的数：深度开中心 `(141,42)`、`depth=0.97628`；关掉变 `(20,68)`；只画远方块 `0.98625` |

### 量这块性能踩的三个坑（都是"度量错误"而不是代码错误）

1. **`clock()` 在 Windows 上量不出亚毫秒**：`CLOCKS_PER_SEC = 1000` 且按调度器时基跳动，
   粒度约 15 ms。第一版用它，把"1000 个实例化"量成 3.9 ms —— 比 10000 个还慢，明显荒谬。
   → 改用 `timespec_get` 的墙钟，并且**同时打印中位数和均值**（一次性尖峰会自己现形）。
2. **垂直同步会把帧钉在刷新率上**：本机 240 Hz = 4.167 ms，于是"提交耗时"里混进了 present 的等待，
   而等待落在哪一组纯属偶然（12000 个三角形"比"120000 个还慢就是这么来的）。
   → 测量前 `lum_window_set_vsync(false)`。
3. **进程刚起来时 CPU 还在升频、驱动也在初始化**：单组内预热 60 帧仍然不够，
   第一组系统性偏慢（0.178 ms vs 稳态 0.009 ms）。
   → **整轮预热一遍再丢弃**（示例里跑两遍，只记第二遍）。

> 三条都属于同一类：**指标本身错了，代码没错**。所以"性能结论"必须能解释得通
> （慢的那个为什么该慢），解释不通就先怀疑度量 —— 这与 M1 那次"先量再猜"是同一条纪律。

### M2 顺手加固的两处（M1 遗留）

- `lum_mat4_look_at`：**先把 `up` 归一化再叉乘**，让退化判据只反映"夹角是否趋零"，
  不再把"up 量级太小"误判成退化（`up = (0,1e-8,0)` 的方向完全合法）；
  同时只保留一个判据（`|u| ≡ |s|`，第二个条件是冗余的）。
- 示例**每帧同步视口与宽高比**（窗口被拉伸时画面不再缩在一角/被拉扁）；
  顺序是"读尺寸 → 设视口 → 设相机 aspect → 重算 VP"，因为宽高比是投影矩阵的输入。

`glimmer_check` 的断言数：52（M1）→ **72**（新增视图矩阵正交归一/手性/落位 13 条 + 加固 2 条）。

## 3c. M3 · 材质与贴图（已完成）

**目标**：把"同色积木"变成"有贴图的物体"，并且**批次不随物体数增长**。

### 三件事

| 事 | 做法 | 为什么这样做 |
|---|---|---|
| **顶点加 uv** | `lum_Vertex3d` = 位置(12) + 法线(12) + uv(8) = **32 字节**；立方体每个面拿到完整的 0..1 贴图 | 贴图必须知道"这个像素取贴图的哪儿" |
| **纹理标 sRGB** | 新增 `Lum_Texture_Flag_Srgb` → 内部格式用 `GL_SRGB8 / GL_SRGB8_ALPHA8`；仅 3/4 通道合法（GL 3.3 core 没有单通道 sRGB sized 格式），单通道传了会明确报错 | 光照必须在线性空间里算 |
| **材质与绘制的批次单位** | `lum_Material3d`（albedo 贴图 + 基色 + uv 平铺）；绘制接口从"传颜色"改为"传材质"：`draw_mesh(mesh, material, model)` / `draw_instanced(mesh, material, models, count)` | 批次单位变成 **（网格，材质）**：draw call 数 = 网格数 × 材质数，**与实例总数无关** |

### 设计决定：`lum_Material3d` 与 `lum_Material` 同住一个文件

- `lum_Material`（既有）= **通用容器**：任意 shader + 4 贴图槽 + 16 个按名字设置的自定义参数，语义由使用者定义，2D 渲染器在用。
- `lum_Material3d`（新）= **固定语义**：3D 渲染器内置着色器认识的几个字段（albedo / 基色 / uv 平铺）。不走"字符串查 uniform"那一套，名字打错不可能发生。

两者是同一个概念（材质）在两种渲染器下的两种形态，所以放在同一个头里（与 `lum_Camera2d/Camera3d` 同住 `lum_camera.h` 是同一条原则）。

没有 albedo 的材质，渲染器绑**内置的 1×1 白纹理** —— 着色器里永远采样，不存在"有没有贴图"的分支（少一个分支、少一条路径）。

### M3 实测结果（RTX 5060 / GL 3.3，640×480 探针 + 960×600 示例）

| 判据 | 实测 |
|---|---|
| **uv 与采样方向** | 2×2 四色贴图贴 +Z 面，按象限采样：左下**(166,0,0)**=红、右下**(0,166,0)**=绿、左上**(0,0,166)**=蓝、右上**(166,166,0)**=黄 —— uv 镜像、上下翻转、行列转置中的任何一种都会让这条断言失败 |
| 光照因子自检 | 四个读数都是 166 = 255 × 0.65，而 0.65 = 环境光 0.28 + 0.72 × lambert(0.514) —— **与手算精确吻合** |
| **sRGB A/B（可量化）** | 同一张中灰(128)贴图：不标 → 输出 **83/255**；标 sRGB → 输出 **36/255**，**比值 0.43（低 57%）**。与理论一致：采样值 0.502 → 线性 0.216，再乘同一个 0.65 光照因子 |
| **批次数不随物体数爆炸** | 4 个材质 × 1024 个实例（共 4096 物体）：按材质分组 **draw_calls = 4**（= 材质数）；逐物体提交 = 4096。提交耗时 **0.200 ms vs 10.536 ms/帧（快 52.7×）** |
| M1/M2 判据在新通路上复验 | `glimmer_instancing` 的 draw call 自检仍全过（实例化没被材质改动破坏） |

### ⚠ sRGB 只做了"一半"（必须记住的陷阱）

标了 sRGB 之后画面会**明显变暗** —— 这不是 bug：

```
贴图侧：sRGB → 线性  ✅ 已做（M3）
光照：  在线性空间算  ✅ 已做（本来就该）
输出侧：线性 → sRGB  ❌ 还没做（属于 HDR / 后处理，M7）
```

也就是说，现在这条链是**半条**：采样被线性化了，但写进帧缓冲的值没有被编码回 sRGB，于是显示器按 sRGB 解释线性值 → 偏暗。M7 补上输出编码（或渲染到 sRGB 帧缓冲）之后就正确了。

**另一条更容易酿成事故的规则**：sRGB 标志**只能标颜色贴图**（albedo、自发光）。法线贴图、粗糙度、遮罩、金属度这些是**数据**不是颜色，标了 sRGB 会让数值被错误转换 —— 这类 bug 表现为"光照方向莫名其妙"，极难查。已经写进 `lum_texture.h` 的注释里。

### M3 相对计划的两处偏离（都是 YAGNI）

| 计划里写了 | 实际 | 理由 |
|---|---|---|
| 顶点**布局描述符** | 没做，仍是单一固定格式（32 字节） | M3 只有一种格式。为它写描述符等于为一个还不存在的需求付抽象成本；等 **M8 载入 OBJ**（可能有/没有法线、有/没有 uv）真的出现第二种格式时再做，那时也只需改 `lum_mesh_create` 里的属性设置一处 |
| 纹理**浮点**标志、**各向异性** | 没做，挪到 **M7** | 浮点纹理需要"以 float 指针上传像素"的新入口，那是 HDR 的活；各向异性在 GL 3.3 里是**扩展**（核心是 4.6），需要扩展探测，理应和 mipmap/MSAA 的过滤质量一起做 |

## 6. 每期的施工流程（照做）

**开工前**
